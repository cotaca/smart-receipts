# OCR extraction (German receipts only)

- Two functions: `parse_receipt_text(text)` is pure and tested without Tesseract; `extract_receipt_data(bytes)` runs `preprocess_image` (EXIF rotation matters for OCR too) → `image_to_data(lang="deu", config=OCR_CONFIG)` → `_ocr_lines` → `parse_ocr_lines` (which wraps `parse_receipt_text`). It raises whatever preprocessing raises, plus `TesseractNotFoundError`.
- **`OCR_CONFIG = "--psm 6"` is load-bearing.** Default PSM 3 reads a receipt as two columns (all labels, then all numbers), so `SUMME` and its amount never share a line. Measured on one image: PSM 3 → `None`, PSM 4 → `208,08` (wrong), PSM 6 → correct. A regression test asserts the config reaches `image_to_data`; removing it breaks the feature while every other test stays green.
- **Confidence filter and low-quality flag**: `_ocr_lines(data)` groups `image_to_data`'s per-word output by `(block_num, par_num, line_num)` into `(text, mean word conf)` lines. `parse_ocr_lines(lines)` drops lines below `LINE_MIN_CONFIDENCE = 55` before joining them into text for `parse_receipt_text`, and sets `low_quality = mean(all line confs) < LOW_QUALITY_CONFIDENCE = 60` (or `True` if there are no lines at all). Calibrated against the 5-receipt benchmark below: clean receipts score a mean line confidence of 81-86, hard-to-read ones 39-44, cleanly separated by `LOW_QUALITY_CONFIDENCE`. `LINE_MIN_CONFIDENCE` = 55 keeps the two clean receipts' correct fields intact (a mis-OCR'd "Pe 0,25" at conf 53 was kept as a bogus item below it; "Summe 214,41" — a euro sign misread as "2" — at conf 47 was already excluded).
- **Header rule**: only the line that was *actually* `lines[0]` in the raw OCR output may become the merchant — `parse_ocr_lines` computes `has_header = bool(lines) and lines[0][1] >= LINE_MIN_CONFIDENCE` and passes it to `parse_receipt_text(text, has_header=...)`. If the real header line's confidence was too low and got dropped, `has_header=False`: merchant is always `None` (never whatever unrelated sentence happens to survive as the new first line), and `_find_items` starts at index 0 instead of 1, since that first surviving line is real data, not a header to skip. Without this, a badly-OCR'd header on `bon_rewe` produced a wrong, non-empty "merchant" from a random later sentence — no confidence threshold could fix that without breaking a different receipt the same way.
- **Amount**: the *last* line matching `PRIMARY_TOTAL_KEYWORDS = ("SUMME", "ZU ZAHLEN")` (case-insensitive), skipping `ZWISCHENSUMME`; the final total prints after subtotals. Only if neither is found, fall back to the last match of `FALLBACK_TOTAL_KEYWORDS = ("GESAMT", "ENDBETRAG")` — `"Gesamtbetrag"` also labels a line in the per-VAT-rate breakdown table that prints *after* `SUMME`, so preferring `GESAMT` outright returned that subtotal instead of the total (measured: a REWE scan read 1,87 instead of 2,00). If the keyword line has no number, use the next non-empty line (printers wrap). No match → `None`, never a "largest number" fallback — on a money field a wrong value is worse than none.
  - Regex `(?:\d{1,3}(?:\.\d{3})+|\d+),\d{2}`. The naive `\d{1,3}(?:\.\d{3})*,\d{2}` reads `SUMME 1234,56` as `234,56`.
  - `BETRAG` is deliberately absent: it matches `Rabattbetrag`, `Nettobetrag`, `Steuerbetrag`, `Rechnungsbetrag`, which print after the total — with "last wins" that returned a 2,00 € discount instead of the 20,00 € total.
- **Date**: first `dd.mm.yy(yy)` that is also a valid calendar date (`99.99.2024` is skipped). Two-digit year → `2000 + yy`. Only if no such date is found, fall back to `ISO_DATE_PATTERN = r"\b(20\d{2})-(\d{2})-(\d{2})"` (no trailing `\b`: one scan's OCR glued the date to the following time as `2025-09-10108:49`, which a closing word boundary would reject).
- **Merchant**: `lines[0]` — but only when `has_header` says that's really the header (see above).
- **Line items** (`_find_items`): range is `lines[start : end]`, `start` is 1 if `has_header` else 0. `end` (`_items_end`) mirrors `_find_amount`'s keyword priority but takes the *first* match, not the last (items always print before any total/subtotal line, so the earliest keyword line is the boundary): first line matching `ZWISCHENSUMME` or a `PRIMARY_TOTAL_KEYWORDS` hit wins outright; only if **no** primary keyword appears anywhere does the first `FALLBACK_TOTAL_KEYWORDS` line end the list instead. This ordering matters: an item description that happens to contain "GESAMT" must not truncate the list early when a real `SUMME` line exists further down. No total line at all means `[]`, otherwise payment/tax lines after the total get parsed as items. An item line is a trailing amount with an optional tax class (one or two letters, e.g. `BW`, optionally preceded by `*`/`x` with no space — `0,50xC`, `0,50*C`) and/or a standalone `*`, and a description containing at least one letter (excludes bare quantity lines); default quantity is 1 and `unit_price = total`. An inline quantity in the description (`Milch 2 x 1,29 2,58`) overrides that default and is stripped out of the description. A standalone quantity line (`2 Stk x 0,99`, `0,523 kg x 2,99 EUR/kg`) attaches to the item **before** it if `round(qty × unit, 2)` matches that item's total (REWE style), else it's held and applied to the **next** item line under the same check (Lidl style); no match on either side and it's dropped. `_to_decimal` (shared with `_find_amount`) turns `"1.234,56"`-style text into a `Decimal`.
- **Benchmark** (`backend/scripts/ocr_benchmark.py`, manual): runs the real pipeline against real receipt photos in `data/` (gitignored, not in the repo) inside the backend container, which has Tesseract. `--dump` writes each image's `(text, conf)` lines to `backend/tests/ocr_fixtures/*.json`, which `test_ocr_benchmark.py` replays with no Tesseract needed. Its core invariant: **correct or empty, never wrong** — merchant/amount/date are either the true value or `None`; the returned items' `total_price` values are a sub-multiset (`Counter`, not a set — two items can share a total) of the receipt's true totals; each returned item is also internally consistent (`quantity * unit_price == total_price`, within 0.01). Rejected approaches, both measured worse: a chain-name list (matched "NETTO" from the VAT column on an unrelated receipt) and OCR image preprocessing/binarization (made one scan's amount read *worse*, 2,08 instead of 2,00).
- Tests: `test_ocr.py` covers the parser and the confidence-filter helpers; `test_receipt_extraction.py` mocks `backend.services.ocr.pytesseract.image_to_data` (via `tests/images.fake_ocr_data`) and asserts nothing is persisted. No endpoint test for `TesseractNotFoundError`: `ASGITransport(raise_app_exceptions=True)` re-raises instead of returning a response.
- Tesseract ships in the backend image; native `pytest` mocks it. Running `extract_receipt_data` natively needs Tesseract with `deu` on `PATH`.

## Not built: other receipt languages

UI `language` is not the receipt's language (a German user abroad gets English receipts) — never key OCR off it; use detection or a per-upload choice. Switching `lang` alone is worse than today: the parser is German in three places — `PRIMARY_TOTAL_KEYWORDS`/`FALLBACK_TOTAL_KEYWORDS`, `AMOUNT_PATTERN` (`1.234,56`), `DATE_PATTERN` (`dd.mm.yyyy`; English `mm/dd` vs `dd/mm` is also ambiguous). Full scope: a second parser + tests, `tesseract-ocr-eng` in `backend/Dockerfile` and `.github/workflows/backend.yml`, and the selection mechanism. No hook or abstraction ahead of the second language.
